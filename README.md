# agentmem

四个 agent（`claude` `codex` `kimi` `dsh`）共享的本地记忆。
**无服务器、无账号、无云同步。** 数据全在 `~/.agentmem`。

它只解决三件事：

1. **共享知识** —— 任一 agent 写的，其它 agent 能检索到
2. **撞车预警** —— 我正要动的目录，别人是不是刚动过 / 正在动
3. **归属** —— 每条记忆都知道是谁写的

> **关于这个仓库**：这是作者自己机器上的多 agent 记忆层，按自己的需求写、只在 Windows 11 上实测过。
> 下文的「本机」「实测」都指那台机器。验收脚本和召回基准里有作者本机的路径和私有记忆的 id，
> 直接跑会失败 —— 更适合当设计参考读：真相源选型、检索的实测取舍、自动记忆的「恰好一次」怎么做。
> Linux 的锁没验证过，macOS 上 scribe/review 会拒绝运行（见「已知边界」）。MIT 许可。

## 装

```bash
cd ~/dev/agentmem && npm install
```

## 用

```bash
memo add --title "阿里云 DNS 主机记录只填前缀" --type pitfall --tags dns,aliyun
memo recall 主机记录
memo forget <id> --reason "记错了"   # 追加墓碑，原记录留着但不再被检索到
memo who
memo reindex
```

正文从管道进来时**必须显式加 `--stdin`**：`echo "长内容" | memo add --title "…" --stdin`

（不加就不读 stdin。这是刻意的：agent 多半以管道方式起进程，
“缺 --text 就自动读 stdin”会在那种管道上永久阻塞。）

## 身份（必须配）

每个 agent 用自己的名字，**没有默认值** —— 记错归属比没有归属更糟。

| Agent | 怎么配 | 状态 |
|---|---|---|
| **claude** | `~/.claude/settings.json` → `env.AGENTMEM_AGENT = "claude"` | ✅ 已配 |
| **codex** | `~/.codex/config.toml` → `[shell_environment_policy.set]` 下 `AGENTMEM_AGENT = "codex"` | ✅ 已配 |
| **kimi** | 配置里没有 env 段 → 每次带 `--agent kimi` | 走参数 |
| **dsh** | 配置里没有 env 段 → 每次带 `--agent dsh` | 走参数 |

kimi 和 dsh 的 `config.toml` / `settings.yaml` 里没有注入环境变量的地方，
所以走 `--agent`。把这句写进它们的指令文件即可：
**「记忆用 `memo`，每次带 `--agent kimi`」**。


## 数据长什么样

```
~/.agentmem/
  log/<agent>.jsonl      真相源。append-only，每个 agent 独占一个文件
  presence/<agent>.json  在线状态，TTL 15 分钟
  index.sqlite           派生索引。删掉跑 memo reindex 就回来
```

**日志是纯文本，可以直接 `cat`、可以进 git、可以手改。**
索引坏了不用诊断，删掉重建。

## 三个设计决定，和它们的依据

**1. 真相源是每 agent 一个 JSONL，不是一个 SQLite。**
本机前科：claude-memo 曾被 25 个孤儿进程锁死数据库，那时还只有 1 个 agent。
每个 agent 只写自己的文件 → 写冲突在物理上不存在。

**2. `add` 不写索引，`recall` 才惰性补。**
索引是所有 agent 共用的一个 SQLite；在 `add` 里写等于把写冲突从 JSONL 请回索引上。
实测 100 个并发 `add` 会互相撞锁跑不完。现在 `add` 只做文件追加，无锁无 SQLite。

**3. 检索 = 两段式：粗筛（字面 + 语义，RRF 融合）→ 交叉编码器精排。**

粗筛 = FTS5 trigram（字面）+ e5 向量（语义），RRF 融合取前 30；精排 = `bge-reranker-base` q8 重排。
向量当初被砍掉的理由（「常驻 570 MB × 五个 agent = 2.8 GB」）是**算错的账** ——
那笔账只对常驻守护进程成立，而 `memo` 是短命 CLI：实测加载 574 ms、查询 6 ms、跑完即还内存。

四条实测结论，每条都推翻过一个先前的判断：

- **字面路要按词项 OR，不能整句当短语。** trigram 下短语 = 连续子串，整句查询恒返回 0 条 ——
  这条路曾经**一直是死的**，`·字面` 标记从没出现过，只看结果看不出来。
  不引入中文分词器：trigram 索引本身就是分词器，把查询切成 3 字窗口逐个 OR，
  bm25 的 IDF 自动压低「怎么办」抬高「会话记」。停用词表要跟新说法永远赛跑，IDF 不用维护。
- **字面路只取 12 条，语义路取 30 条。** 两路权重相同、池子封顶 30，所以融合后 ≈ 各路 top-15；
  字面路也取 30 条时会把语义路第 16–30 名整段挤掉，**修召回反而弄丢一条**。
- **精排必须逐条算。** q8 动态量化的 scale 按整批张量算，打成一批会让同一对的分被邻居挪动
  **0.71 个 logit**，而注入门槛就建在这个分上。逐条算之后分数是 `(查询, 条目)` 的纯函数，
  而且**快 3.5 倍**（30 条 555 ms vs 一批 1977 ms —— 批处理把每行补齐到最长那行，短文档全在空算）。
- **注入门槛 2.5，不是 0。** 「0 是模型自带的校准点」是在会摆动的批算分数上得出的，已作废。

`scripts/bench-recall.mjs` 是这些结论的来源：14 条转述型查询（刻意避开标题用词）
+ 8 条字面型查询（粘报错串/标识符）+ 6 条真闲聊，量的是**正确那条排第几**。
（它和 `bench-rerank.mjs` 跑在作者的私人记忆库上，开源版不含这两个脚本。）

## 迁移历史记忆

```bash
node scripts/migrate-legacy.mjs --db <旧库路径>.sqlite

```

幂等，跑几次都一样。归属统一写 `legacy:claude-memo` —— 不假装是某个 agent 写的。

## 自动记忆（claude / codex / dsh）

不用自己想着写。每家的会话结束 hook 都会在后台：

1. **scribe** —— 扫三家新增的会话记录，各用**自己家族的小模型**判断有没有值得长期记住的事
2. **review** —— 候选交给**环形下一家**的模型审，通过了才进库

```bash
memo scribe --init     # 首次必跑：水位对齐到当前末尾，历史不回溯
memo scribe            # 扫一遍，产出候选
memo review            # 交叉审核，通过的进 log
memo pending           # 看待审的 + 被驳回的
```

模型配置在 `~/.agentmem/scribes.json`，**模型名一定会腐烂**所以外置在那里，不写死在代码里。

环是 claude → codex → dsh → claude，**审核者永远是异族**：

| agent | scribe 用 | 审核它的 | 记录 | 唤起 |
|---|---|---|---|---|
| claude | `haiku` | codex 的 `gpt-5.6-luna` | `SessionEnd` hook | `UserPromptSubmit` hook |
| codex | `gpt-5.6-luna` @`low` | dsh 的 `deepseek-flash` | `Stop` hook | `UserPromptSubmit` hook |
| dsh | `deepseek-flash` | claude 的 `haiku` | `Stop` hook（走官方 bridge 插件）| 自写 cordis 插件 |

**scribe 从磁盘读 transcript，不需要跑在被扫的那个进程里** —— 所以任一家的 hook 都能扫全部三家，
日志 append-only，晚扫不丢。

六个接线上的坑，都踩过：
- **codex 把 hook 拉起的 worker 一起杀掉**（2026-10-09 修）：codex 在 Job 里跑 hook、等 hook 的输出关闭，超时（30 秒）
  就终止整个 Job（Codex 第十一轮复核读 0.162 的 `hooks/command_runner.rs`）。旧版 hook 实测约 32 秒、以超时结束 ——
  推测是 `detached` 的 worker 继承了 hook 的输出管道（这一步是推测）。于是 Stop hook 起的 worker 和它叫的模型进程全被强杀：
  10-08 16:47 起约 17 小时，自动记忆**一次都没跑完**，auto.log 里只剩一串开头行，没有任何报错
  （那段时间的触发全来自 codex exec；claude 的 SessionEnd 不杀）。
  修法：Windows 上经 WMI（`Win32_Process.Create`）起 worker，父进程是 WMI 服务、不在宿主的 Job 里、不继承任何句柄（hook 3.5 秒正常结束）。
  WMI 起的进程不继承环境变量（代理 `HTTPS_PROXY` 只在 hook 继承来的环境里），完整环境经 `Win32_ProcessStartup.EnvironmentVariables`
  直接交过去（Unicode），**不落盘、不放命令行**（环境里有 API key；临时目录的权限不可控）。
  worker 用一个随机令牌核对环境交到了没有，没交到就不跑、在 `--home` 指的库里报出来。WMI 起不来就退回 spawn 并在 auto.log 记一笔。
  闸：`node scripts/acceptance-detach.mjs` —— 自己造一个 kill-on-close 的 Job 宿主（`scripts/jobhost.ps1`）。对照组证明它确实会杀
  普通 detached 子进程；实验组用屏障：宿主退出后 worker 必须还停在模型调用里、进程活着，放行后才跑完。
  （这只复现一种杀法；按会话、全局扫描、按 PID 去杀不在覆盖范围内。）
- **WMI 起的进程看不到在 Claude 应用里装的命令**（2026-10-09）：Claude 桌面应用是 MSIX 打包的，在它里面装进 `%APPDATA%`
  的东西被重定向到应用的私有目录，包外看不到。codex 的 shim 就是这样 —— worker 改成经 WMI 起之后，叫 `codex.cmd` 全部报
  「不是内部或外部命令」。已从包外把 shim 装进真实的 `%APPDATA%\npm`。模型那边的报错：字节不是合法 UTF-8 时改按 GBK 解码，不再是乱码（只看「解出来有没有 �」会把合法输出解坏）。
- **会话结束弹窗抢焦点**（2026-10-08 修）：worker 是 `detached` 起的，Windows 上等于**没有控制台**；
  它起的 `memo scribe/review` 没控制台可继承，系统就新建一个可见的，Win11 默认交给 Windows Terminal
  → 每次会话结束弹 2 个窗口、抢 2 次焦点（codex/dsh 的 Stop 每轮回复都触发）。
  修法是 worker 起子进程时 `windowsHide: true`，下面的 claude/codex/dsh 都继承那个隐藏控制台。
  闸：`node scripts/acceptance-nowindow.mjs` —— 枚举真实窗口、盯前台，不查代码里有没有那个选项。
- **codex 的 `hooks.json` 有 `trusted_hash` 白名单**：没登记的 hook **被静默跳过，不报错**。
  登记算法反推出来了，`scripts/codex-hook-trust.mjs --verify` 先对现有条目验 7/7 再写。
- **codex 的注入要 `systemMessage` 和 `additionalContext` 两个字段都给**，单给任一个实测都不生效。
- **dsh 官方 bridge 的 `UserPromptSubmit` 不触发**（根因未确认），所以唤起改走自写插件
  `dsh-plugin/`。它装在 pnpm 管的 `node_modules` 里，**`pnpm install` 会静默抹掉它** ——
  恢复：`node scripts/install-dsh-plugin.mjs`。

### 四道闸，三道不需要信任模型

| 闸 | 判定方式 | 挡掉什么 |
|---|---|---|
| 窗口内没有写操作 | 脚本 | 「一整天在读代码」的会话，**根本不加载模型** |
| 引证在原文里找不到 | 脚本 | 编造。片段先逐字找、找不到再宽松找（忽略空白和引号样式），**每个省略号片段都要找到**，切在数字中间的那一处不算（接着往后找）；找到之后，交给审核者和留档的是**按位置从原文摘出的原文**，带上下文：相距 400 字内的片段连同中间省略的原文一起给，两头扩到所在句子再多一句，停在半个词 / 数字上就补完，没到句子边界标 `…`，每段最多 2000 字。模型写的引文另存 `modelQuotes`。对不上会**带着错重问一次**，两次都对不上才丢 |
| 与已有记忆**逐字相同** | 脚本 | 已经记过的（只挡逐字相同；相似度 ≥ 0.96 的照常发布，把库里那条交给审核者对照，见下） |
| 交叉审核 | **异族**模型 | 流水账 · 没有判据 · 把一次性细节写成普适规则 |

**审核者不可用时候选留在 `pending/`，绝不默认放行** —— 默认放行等于没有审核。

**scribe / review 叫的模型一律不许用工具**（2026-10-12 加，`memo scribe` / `memo review` 会拒绝跑缺了这些参数的配置）：
claude 带 `--tools "" --strict-mcp-config --permission-mode dontAsk`，codex 带 `-s read-only`，dsh 由代码强制
`DSH_PERMISSION_MODE=read-only`。送进模型的会话片段是**不可信输入** —— 当天实测：scribe 叫的 `claude -p --model haiku`
带着全部工具和 MCP、继承了用户的权限设置，读到的片段里正好有一份代码复核报告，它就动手改了 agentmem 自己的
`lib/scribe.mjs`（没有任何人要求，被发现后杀掉进程、改动另存后撤回）。

### 不丢、不重复：靠互斥，不靠协商（2026-10-08 重做）

| 机制 | 防什么 |
|---|---|
| **auto 锁**（命名管道）| 一阵触发同时起好几个 worker。codex/dsh 的 Stop 每轮都触发，scribe/review 调 `codex exec`/`claude -p` 时还会触发它们自己的 hook，auto.log 里见过 1 秒 5 次 |
| **writer 锁**（命名管道，scribe 和 review 共用）| 手动 `memo review` 和后台的撞车；同一时刻只有一个进程在改水位 / pending / log |
| 模型调用失败 → **水位退回**，同 agent 本轮熔断；日志记下模型自己报的原因 | 运行故障（掉登录、断网、额度）把会话当成「看过了」永久跳过 |
| review 时某个审核者**连续两次**运行失败、或者本轮失败**累计耗时**到两倍单次超时（10 分钟）→ **本轮不再叫它**，它负责的候选留待下次；总结行写「本轮不可用，跳过 N 条」。中间成功一次连续计数清零（累计耗时不清）；**这一条候选**的问题（提示拼不出来、提示超过命令行上限）只扣下这一条、不计数。一轮 review 开跑 20 分钟后不再开始新的调用 | 审核者接口一直报错（2026-10-10 dsh 连续 502）时，review 对着它连撞上百次，30 分钟的步骤时限耗光，别的审核者能审的也审不完；失败和成功交替时连续计数总被清零，七次超时就是 35 分钟；反过来，一条坏候选也不能让好好的审核者整轮停摆 |
| 经命令行收提示的模型（dsh）：命令行长度按 libuv 的真实规则算（验收 29v6 在真实 Windows 上量过：正好 32767 字含 NUL 的能起、多一个字的拦下），载体是 cmd.exe 的按 8191；**段按转义后的长度切**，每段都放得进命令行；重问时附的错引文最多 1000 字；万一还是送不出去，**这个文件停在这一段、水位不动**，别的文件照常做；提示原样代入，不经替换模式展开 | 一段送不出去就跳过 = 当成「看过、不值得记」，而它一个字都没送出去（第十八轮复核）；当运行故障处理又会每轮熔断这个 agent；会话里的 `$&` `$'` 被 `String.replace` 展开，送给模型的提示被悄悄改掉 |
| 发布候选分三步：写 `.tmp`（记下它覆盖的窗口）→ **存水位** → 改名；下次开头对账遗留的 `.tmp`：水位已越过它就补发布，**能证明**没越过、且源会话还在扫描范围里才作废，其余（元数据缺失/为空、源会话不在了、作者已不在配置里）一律隔离 | scribe 在两步之间被杀：要么重跑把同一段再产一条（重复），要么这段内容再也没人处理（丢失）。**恰好一次** |
| 候选、水位、驳回留档都先写临时文件再改名 | 写到一半被杀，留下读不出来的文件 |
| 大窗口**切成每段 ≤24000 字逐段交给模型**（尽量切在一轮提问的开头）、**每段做完立刻存水位**（没有候选的段也存）；某段失败水位只退回到这一段 | 原来只喂窗口最后 24000 字、水位却越过整个窗口 —— 断线后的积压，前面那部分没被看过就标成看完了；中途被杀时已判完的段全部重问 |
| **续做标记**（水位表里的 `#continue`）：过了预筛、没做完的窗口，下一轮从水位接着做，**不再预筛**；**只做到原窗口的终点**，之后追加的内容当新窗口 | 唯一的写操作在已经做完的那一段里，剩下的后缀被重新预筛成「没动过东西」或「太短」，直接越过、从来没送进模型；续做终点跟着文件末尾长，一直追加的会话永远处在续做里，后面的文件轮不到 |
| **每家每轮最多叫 20 次模型**（`AGENTMEM_SCRIBE_MAX_CALLS` 可调，**重问也算**），到了停在段的起点、下一轮接着做 | 几十万字的积压一轮叫几十次模型；再被 auto 的 30 分钟时限杀掉，就是反复付费不推进 |
| 窗口**太短（不足 200 字）就不推进水位**，等后面的内容攒上来一起看；会话**两小时没动静**就照常送一次；没动过东西才越过 | dsh 的轮次概要截断到「提问 50 字、回答 120 字」，单独一轮最多 177 字，而 dsh 每轮回复都触发扫描：每一轮都不足 200 字、被越过，永远看不到；会话停在短尾上时那段永远不送 |
| codex 同一条消息的两条记录按 id **只认整个文件里第一次出现**；去重**只比对已进库的**，不比对还没审的候选；**只有逐字相同才直接挡**，相似度 ≥ 0.96 的照常发布、把库里最像的那条（id、正文、相似度）一起交给审核者判「是不是同一件事」 | 切段或窗口边界落在两条记录之间时，同一条消息被送两次；拿没审过的候选去压新候选；e5 对两条不同事实（端口 3001 / 3002）给到 0.988，按相似度直接挡就把不同的事当「已记过」丢了，水位越过、捞不回来 |
| dsh 会话按**已结束的轮次**一轮一行（第 n 轮在第 n-1 行），还没结束的那一轮不算；旧水位**在开扫之前一次换算完、立刻落盘**（`--init` 时不换算）；dsh 的暂存带坐标版本，没带的旧版暂存一律隔离 | 旧切法把「待办」「动过东西」这两个状态排在各轮后面，新的一轮插到它们前面，水位按位置记就错位了；只在内存里换算的话，暂存了新坐标的 `.tmp`、存水位之前被杀，下次对账拿旧水位比新窗口，判错；`--init` 读失败退出时别家的水位已被换算落盘 |
| review **原地**处理候选；先查这个 id 有没有**完整的**结论（log 逐行解析、rejected 按 id），读不了就留待重试 | 在「写结论」和「删候选」之间被杀，下次再写一遍；半截行被当成「已进库」把候选删掉；同一个 id 一份驳回一份通过 |
| 每条记录前后都带换行（`\n{…}\n`），不看文件尾；「完整」= 能解析（索引和 review 用同一个定义） | 新记录接在别人留下的半截行后面一起坏掉 —— 先看文件尾再决定的写法有竞态（看完之后才出现半截行），Codex 第五轮实测打穿过；正写到一半时建索引，那一行永远进不了索引 |
| **读失败就整轮不跑**：水位表、对账、`--init` 读不了一律退出，只有「读出来但解析不了」才按写到一半处理 | 把读错误当成「空」：把已提交的候选当未提交删掉（丢失），或者跳过对账接着推进水位（日后重复） |
| 读不出来的候选、解析不了的 `.tmp` 都挪成 `.corrupt`，不删 | 坏文件把候选静默删掉；`.tmp` 写完之后被损坏，水位其实存过，删掉就永久漏了 |
| review 写完 log **回读确认**自己那条完整了才删候选；`memo add` 回读不到就重写一次，还不行报错 | 一次追加被短写拆开、中间插进别人的写入，记录坏掉，候选却已删掉（或 add 打印「已记录」其实没记上） |
| 旧版留下的 `.claimed` **不自动接回**，只在 `memo pending` 里列出 | 升级那一刻还活着的旧版 review 和新版一起提交 |
| hook 起不了后台 worker 也以 0 退出 | 记忆系统弄坏会话收尾 |

**已知边界**（不是没想到，是有意留着的）：
- `memo add` / `forget` **不拿锁**：agent 高频调用，不能被一个跑几分钟的 review 挡住。代价是可能和 review 同时追加同一个文件，靠「先隔开半截行」兜底。
- Linux 的锁走抽象命名空间 socket，**本机没验证过**；macOS 拿不到锁，scribe/review 会拒绝运行（宁可不跑，不可并发）。
- 「两次写入之间被杀」靠**故障注入点**测（环境变量 `AGENTMEM_FAILPOINT`），「读出 EIO」靠读失败注入（`AGENTMEM_FAULT`）——
  后者在 Windows 上对正常文件造不出来。不设这两个变量时都只是一次字符串比较。
- log 里记录之间有空行：那是「每条前后都带换行」的代价，所有读 log 的地方都跳过空行。
- **旧水位里可能已经漏了一行**：2026-10-08 之前，会话读取器会把文件尾的半截行也数进水位。
  如果当时正好扫到一个写到一半的会话，那一行已经被越过，新代码也补不回来。
  不能统一减一（那会重扫已经处理过的行），也没有历史窗口记录能判断哪些会话受影响 —— 记着，不修。
- **dsh 的只读预设没有实测过**：加上 `DSH_PERMISSION_MODE=read-only` 时 dsh 接口一直报 502，等它恢复后要验证一次
  「让它写文件、文件不出现」。
- **`.cmd` 包装的模型超时时，孙进程可能还活着**：超时只杀得掉 cmd.exe 本身（Codex 第十八轮复核实测）。
  scribe / review 叫的模型已经不许用工具，残留的进程只占资源、不会动文件。
- **单独一行就超过 24000 字时只看这一行的尾部**：大窗口已经按段切开、逐段交给模型（见上表），
  只有一条消息本身就超过上限时才不得不截断。截断会在 stderr（auto.log）里报出是哪个文件第几行、多少字，
  但水位照样越过它 —— 截掉的部分不会再被看。
- **原文摘段只是原文的一部分**：限定条件写在两句以外、或者远处另一段（「以下都禁止……」隔了好几句）时，审核者看不到。
  任何有限长度的摘段都兜不住这种情况；审核提示里如实说了「摘段只是一部分」，再往下只能靠人看。
  摘段逻辑每修一次就升一次版本（当前 `source-span-v4`）。旧版本的候选审核前会**按现在的规则重新摘段**，前提是内容核对得上：
  v4 起的候选存了整段窗口的哈希（`windowSha`），必须一致；更早的只存了窗口最后 3000 字（`excerpt`），重新拼出的窗口末尾必须和它
  **整段相等**，窗口更长时前部核对不了，重摘出的每一段都必须落在这 3000 字里。核对不了的（太老、没有窗口信息、
  旧切法的 dsh、会话被同路径重写过、引文在核对不了的前部）审核提示里标成「不能当事实」。
- **句子边界只认中文句末（。！？）和换行**：英文 `. ! ?` 会出现在路径、URL、引号里的值中间，白名单永远补不完。
  代价是英文内容多带点上下文。中文句末也可能在值里（`"甲！乙！丙"`），所以摘段**只要没到原文两端就标 …**，
  停在句子边界上也标 —— 值也许不全，但不会装作是全的。
- **一个问题和它的回答仍可能分在两段**：切段优先落在提问开头，但一轮回答本身超过半段时只能在回答中间切，
  后一段的模型看不到问题。
- **dsh 换了切法**（2026-10-09）：旧水位一律按「旧水位减 3、且不超过已结束的轮数」换算（旧水位里最多 3 行不是轮次），
  宁可多看两轮（可能多产一条重复候选），不能少看。不能用「旧切法下现在有几行」判断看没看过：dsh 每轮开始会清空待办，
  长度不变而多了一轮（Codex 第十轮复核）。**旧切法已经吞掉的轮次救不回来**。dsh 的待办（todos）不再提取：它会被改写，
  没有稳定的位置，内容在各轮对话里本来就有。
- **太短的结尾要等两小时才送**：会话停在一段不足 200 字的内容上，那段先等着；文件两小时没再写过才送一次。
- **「是不是同一件事」现在由审核者判**：e5 对中文的相似度整体偏高，两条不同事实（服务器 A/端口 3001 与 B/3002）量到 0.988，
  「同一件事换个说法」才 0.9702 —— 两个分布重叠，没有一条线分得开，所以相似度只用来找「库里最像的那条」交给审核者对照，
  不再直接丢。审核者判错了也会留档在 `rejected/`（能捞回来），不像原来那样水位越过、候选没了。代价是近似重复多一次审核。
- **同一件事在审核前可能有两条候选**，都通过就进库两条：重复比丢失好。
- **手工恢复 `.corrupt` 之前先核对**：隔离只说明「不确定它提交过没有」，不说明「肯定没处理过」。
  它的窗口可能已经被重做、产出了另一个 id 的候选；直接改回 `.json` 会让同一段内容以两个 id 进库
  （review 只按 id 判重，Codex 第八轮复核实测）。`memo pending` 里标「隔离」的是内容完整的，标「坏文件」的是读不出来的。
  接回步骤：① 看它的 `sourceFile` / `window` / `layout` 和水位表里这个会话的水位；② 在 `log/`、`pending/`、`rejected/`
  里找有没有同一段内容的结果（按标题、按 window）；③ 没有的话，先把配置恢复成产生它时的样子（作者不在配置里而被隔离的，
  先把那个 agent 加回来），再把文件改回 `.json.tmp`、跑一次 `memo scribe` 让对账重新判；④ 坐标版本不明的旧 dsh 暂存
  **不要**整批改成 `.json`。
- **读不了就整轮不跑**意味着坏掉的水位表或 `.tmp` 会让自动记录一直停着。原因会写进 `~/.agentmem/auto.log`，
  但**没有主动提醒** —— 不看日志就不知道。读不了的会话文件只跳过它自己，同样记在日志里。

**为什么用命名管道而不是锁文件**：锁文件判「持有者死没死」只能看时间，于是要有过期、接管、心跳，
而这三样一起是一串竞态 —— 旧版实测：5 个 worker 撞上一把陈旧锁，**5 个全跑了**。
命名管道同一时刻只能有一个进程监听，进程一死（哪怕被强杀）系统立刻收回。
review 原来那套「认领」（原子改名 → 按时间回收 → 加随机后缀 → 确认所有权）也是同一个病：
让并发的进程互相协商，每补一层都还剩一个更窄的窗口，两轮 Codex 对抗式复核都用注入时序打穿了。
不让它们并发，那些窗口就都不存在了。

中间走过一条弯路，记在这里免得再走：用「会话文件 + 窗口起始行」的哈希当候选 id，重跑就得到同一个 id、不会重复 ——
但重跑时会话可能已经变长，窗口起点相同、内容更多，id 却一样，被当成「已进库」删掉，**多出来的那段永久丢失**。
那是把「可能重复」换成了「可能丢失」，更糟（Codex 第四轮复核指出，验收第 29b 条复现）。

验收：`node scripts/acceptance-scribe.mjs` 第 15–33 条（含 29b–29u）+ `acceptance-core.mjs` 第 9–13 条
+ `acceptance-detach.mjs`（worker 活过宿主）+ `acceptance-nowindow.mjs`（不弹窗）。
依赖时序的几条用**同步屏障**排顺序（测试桩按先后领号，测试决定谁停、谁先醒），不是靠「拖 1.5 秒碰运气」；
每一处修复都做过变异验证（拿掉它，对应的那条必须变红）。

### 两个量出来的数

**去重阈值 0.96 不是拍的。** 同一件事换个说法 0.9702 · 同领域但不同的事 0.8837 · 跨领域 0.8884。
e5 对中文相似度整体偏高（真·无关的两条也有 0.88），能用的缝只有 0.89–0.97，0.96 落在中间。

**「核实忠实性」不能交给模型。** 早先把整个 16000 字窗口喂给审核者，
`gpt-5.6-luna@low` 判成「源片段未提及」—— 而那些词在源里出现了 13 / 5 / 2 / 2 次。
大海捞针式的核对便宜模型做不了，结果是**系统性误驳**。
所以改成 scribe 交出引证、脚本逐字核对，审核者只看短上下文里的可复用性。

### 当前的诚实状况

真模型实测通过率约 **1/4**。被驳回的多数理由站得住（正文用了引证之外的事实、
把一次性清单写成通用规则），但这个闸**偏精度、不偏召回** ——
进库的质量可信，代价是会漏。想放宽就改 `lib/scribe.mjs` 里的审核 prompt。

**它补充而不取代主动 `memo add`**：「这个项目不值得做」这类战略判断，scribe 在 transcript 里看不出来。

**召回的已知上限（2026-09-28 量出来的）**：22 条查询里 **20 条粗筛都能捞到**，
所以瓶颈**不在粗筛**；卡住的是 4 条**用词完全不重叠**的 ——
比如问「第一次跑自动记录把所有历史会话都翻了一遍」，库里那条叫「无初始化水位导致冷启动爆炸」，
把这一对直接交给精排也只有 −4.39，只有字面出现「冷启动」才给 +2.94。
**不是池子太小**（加大池子对它无用，已实测），是交叉编码器接不上这种零锚点的转述。
要治只能上查询改写／HyDE，那意味着每条 prompt 多一次模型调用 —— 当前不做，记着这个上限。
